# Background Dreams locations

Migration `0010_dream_locations` adds one durable, owner-scoped job per save. Migration `0011_dream_google_identities` adds a separate table containing Google Place IDs, the user's selected ID, an input fingerprint, and cache-expiry metadata. Both are additive: existing tables, captions, names, notes and board membership are not rewritten. Downgrades refuse to delete evidence or user choices.

New saves, parse completion, and review edits queue work in the same database transaction. GET item responses only read saved state. A scheduler discovers up to 25 previously unprocessed named saves each minute, including older saves whose `needs_google_places_lookup` is false. This does not reparse captions. Missing names remain saved for ordinary review.

The dedicated `dream_locations` queue uses one worker process. Flight imports keep their existing default queue and worker. Jobs use a 120-second lease and compare the current identity and pin fingerprints before applying a result. Duplicate notifications are harmless; abandoned leases and lost broker notifications recover on subsequent scheduler ticks. Temporary failures retry with exponential delays, at most five attempts. Missing or rejected provider credentials report `blocked` and retry after six hours; an explicit retry can run sooner. Google's first compatible result populates the map automatically; users do not need to approve a pin. Known country, city, name or venue-type mismatches are filtered before choosing a result, and Google relevance order is preserved. Provider failures never delete saves or invent city-centre pins.

True user-supplied coordinate pins remain authoritative. A confirmed Google Place ID survives retries, cache expiry, notes/tags and category edits. Changes to the saved place name, city, country, region or explicit pin invalidate that Google selection; its ID remains in decision history. Automatic refresh fetches the same selected ID, never silently searches for a replacement or follows a moved-place ID.

Google names, addresses, types, attribution payloads and raw responses are never stored in SQL, Redis, saved-item metadata or history. Only coordinates are cached in a dedicated **nonpersistent** Redis service for 29 days. SQL/history contain IDs and application state only, so database backups contain no new Google coordinate/content cache. API reads check expiry independently of Redis eviction and hide missing/expired coordinates. Existing unversioned Google payloads are never treated as manual pins or serialized as current coordinates. Genuine manual URLs and historical non-Google evidence keep their existing behavior.

This follows Google's [Place ID storage and attribution policy](https://developers.google.com/maps/documentation/places/web-service/policies) and the [Places API caching/map restrictions](https://cloud.google.com/maps-platform/terms/maps-service-terms). Google-derived locations must appear on Google Maps. Live Google names/addresses must carry Google Maps branding and any returned third-party attribution. Original user/reel labels remain the saved-item labels.

## Configuration and deployment

New unresolved jobs use Google Places (New), with no legacy default key or provider fallback. Search starts with an IDs-only Text Search. A singleton gets Place Details Pro; ambiguous IDs get one bounded Text Search Pro. There are at most two requests per search, with explicit field masks and a 30-second total deadline. A singleton alone is not proof of a match. Country, name, locality, compatible category and precise-POI validation determine whether it resolves or has no reliable result. Administrative geography, local-script city names and distinctive transliteration matches can resolve automatically. The result is stored as resolved with location_user_confirmed=false; automatic matching never claims user confirmation. Parking, transport, street/area centres and moved/closed places are excluded. The [Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search) and [Place Details](https://developers.google.com/maps/documentation/places/web-service/place-details) docs define field-mask billing; no wildcard, rating, photo, review or phone fields are requested.

The scheduler checks selected-point cache health in bounded batches, normally every five minutes per selected item. It refreshes missing caches or coordinates within one day of expiry. Valid coordinates remain available during refresh; expired coordinates never reappear through URL or legacy-field fallbacks. Redis uses a shared connection pool, short timeouts and a fail-closed outage circuit so a large item list does not multiply cache timeouts. Existing Google needs_review rows are picked up in bounded scheduler batches and searched again with current saved inputs. They resolve automatically or end as not_found; the same row is not repeatedly reset. Original saves, manual pins and confirmed selections remain unchanged, and historical candidate IDs are retained in resolution history. This change needs no new schema migration. Other terminal results retain their existing explicit retry behavior.

Configure `GOOGLE_PLACES_API_KEY` only in the protected backend environment, restricted to Places API (New) and the server egress IP. Configure `GOOGLE_PLACES_CACHE_URL` for a separate Redis cache with persistence disabled, no mounted data volume and no backups; there is deliberately no fallback to the persisted Celery broker Redis. Never copy source-code defaults, print expanded environments, or ship this server key in the app. Native Google Maps uses a separate Android package/signature-restricted key. Missing/rejected provider configuration yields `blocked`; cache failure preserves the save and retries without storing Google content.

Optional limits: `DREAM_LOCATION_ENABLED=true`, `DREAM_LOCATION_BATCH_SIZE=25` (maximum 100), and `DREAM_LOCATION_MAX_ATTEMPTS=5` (maximum 10). Disabling the feature pauses provider work without deleting queued records or saves.

Before rollout, take a verified PostgreSQL backup and rehearse `alembic upgrade head` on a restored copy. Compare every original table's rows/schemas, then run synthetic lifecycle checks. Apply migration 0011 and configure the dedicated ephemeral cache before starting the updated backend. Keep exactly one beat and retain the prior backend image for rollback. Do not restore/delete data to roll back code. Worker commands remain:

```sh
celery -A app.celery_app.celery_app worker --queues=dream_locations --concurrency=1 --prefetch-multiplier=1 --hostname=locations@%h
celery -A app.celery_app.celery_app beat
```

Keep the default Gmail worker running. Verify API, default worker, location worker, scheduler, broker and ephemeral cache independently. API readiness alone does not prove Google credentials. Test a bounded authorized lookup without logging provider payloads, then retry only intended owned items and verify every original saved row remains unchanged.

## Authenticated API

- `POST /dream-items/{id}/locate`: queue/retry an unresolved item; returns `DreamItemOut`. Existing confirmed or resolved pins are preserved.
- `POST /dream-items/{id}/location-confirm` with `{ "candidate_id": "..." }`: confirm one current candidate belonging to this item; returns `DreamItemOut`. Foreign-owner IDs return 404; stale or unrelated candidates return 422.
- `GET /dream-items/{id}/location-details`: fresh Google names, addresses, candidate coordinates and `location_attributions: [{display_name, uri}]`. At most five same-ID Details calls, with an 18-second overall response deadline. It never queues jobs or writes SQL/cache. Requires `X-Trotter-Maps: google`; incompatible clients receive 409 before any provider request. Temporary provider failures return 503 for an explicit retry; unavailable/obsolete candidates may return an empty successful response. Responses use `Cache-Control: private, no-store`. Fetch when details/review opens, cancel on close/account change, and never retain this content in global/persisted client state. A Google confirmation fetches that candidate's details again before applying the choice, and rejects concurrent edits.
- `POST /dreams/locate-missing` with optional `{ "item_ids": [1, 2] }`: queue named missing pins for those owned items; omitted IDs cover all of the user's saves. Returns `{ "queued": 2, "items": [...] }`. A request containing any inaccessible ID fails atomically with 404.

Item responses retain existing location fields and add `location_place_id`, `location_candidate_ids`, `location_expires_at`, and `location_user_confirmed`. Google list/poll responses use provider `google_places`, retain original saved labels, and return null address/empty candidate payloads; only IDs and unexpired cached coordinates are serialized. Fresh details return `location_candidates`, `location_address`, `location_attributions`, status/selected ID and `location_expires_at`. Internal job leases/history are not exposed. List polling makes no Google requests. Normal item responses expose Google coordinates and expiry only to clients sending `X-Trotter-Maps: google`; older clients receive no Google pin coordinates or coordinate-derived URLs. Original manual and Geoapify pins are unaffected.

When a named save has no existing or resolved Maps URL, responses provide an encoded Google Maps text search for its name, city, and country. This read-only fallback never writes a saved URL or coordinates; numeric-looking names are explicitly treated as place searches. Unnamed saves receive no city-only fallback, and existing saved or resolved links take precedence.

## Offline verification

Run with `DATABASE_URL=sqlite:///:memory:`, empty provider keys, dotenv disabled, and network blocked. Allow only Windows asyncio's internal socketpair if testing on Windows. From the repository root:

```sh
backend/.venv/Scripts/python.exe -m pytest backend/tests/test_google_dream_place_search.py backend/tests/test_google_location_lifecycle.py backend/tests/test_google_location_api.py backend/tests/test_dream_google_schema.py backend/tests/test_dream_locations.py backend/tests/test_dream_location_schema.py backend/tests/test_dream_coordinates.py backend/tests/test_dreams.py backend/tests/test_dream_place_search.py -q
```

These tests use synthetic data and mock providers, including stale results, ownership, manual edits, lease recovery, retry bounds, lost broker messages, and full preservation of prior rows. PostgreSQL DDL compilation is covered locally; an actual PostgreSQL restored-copy rehearsal remains a separate rollout check.
